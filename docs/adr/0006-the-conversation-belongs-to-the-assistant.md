# The conversation belongs to the assistant

A follow-up about a source resumes the assistant's own session rather than starting a new
one. That makes the assistant persist the conversation — transcript, questions and answers —
on the person's machine, under the assistant's control. Yoinks accepts this and scopes its
promise accordingly: **Yoinks saves nothing.** An answer is still shown and discarded by
Yoinks, and is still never an artifact; the record the assistant keeps is the assistant's,
exactly as its history of any other chat is.

## Why

Resume is what makes a second question cheap. The first turn carries the whole transcript;
every later turn — a new question, or an expansion of a shown fact — sends only itself,
because the assistant already holds the source in context. Without it, every follow-up
re-pays the full transcript in latency and tokens, on a product whose entire point is being
faster than watching.

The cost is that the old README claim, "answers are displayed and thrown away; nothing is
saved," stops being literally true of the machine as a whole. It was never true of the
machine as a whole: an assistant on the PATH ([ADR 0002](0002-drive-an-assistant-on-path.md))
has always been free to keep telemetry, logs and history of what Yoinks pipes through it.
The claim Yoinks can honestly make, and the one that matters, is about what *Yoinks* does:
it writes no answer to disk, keeps no archive, and holds only a handle to the conversation —
dropped when the person leaves the source (`CONTEXT.md`, **Conversation**).

What ADR 0001 and [ADR 0005](0005-a-fact-that-cannot-be-checked-is-not-shown.md) actually
protect is untouched. Checkability is enforced per turn: every resumed answer and every
expansion passes the same parse, and a fact whose timestamp is not a block this source has
is still dropped. Persistence and provenance are different axes.

## Considered options

- **Refuse persistence, keep follow-ups.** Re-send the transcript and the prior turns as a
  fresh one-shot prompt each time. No session file, but every follow-up pays the full
  transcript, long sources hit limits sooner, and the purity bought is about a file the
  person's own tool writes in the person's own home directory.
- **Refuse follow-ups.** Keep the one-shot shape. Rejected because it caps the product at
  one question per fetch, and the validation evidence (`docs/validation/step-2-cold-start.md`)
  was generated by exactly the multi-turn shape this adopts.
- **Disable the assistant's persistence.** Flags exist (`--no-session-persistence`), but a
  session that is not persisted cannot be resumed, which is the whole mechanism.

## Consequences

- The README and any other public wording say "Yoinks saves nothing" and name the assistant
  as the keeper of the conversation. The stronger claim is retired everywhere it appears.
- Yoinks holds one session id per source and drops it when the person leaves the source. A
  handle held longer than that would quietly grow into an archive feature, which the
  2026-07-25 session already established nobody wanted.
- The audience cost of ADR 0002 does not grow: this uses the same assistant, found the same
  way, with resume invocations verified against the real CLIs before shipping — the same
  rule `src/lib/assistant.ts` already states for first-turn invocations.
